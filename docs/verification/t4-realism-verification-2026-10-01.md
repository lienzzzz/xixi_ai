## 5. Findings

严重度按"对完成标准的影响"定，不按"修起来麻烦"定。

### F1（low）提问率在 Run A 跳出 30–50% 参考带的下沿：26.3%
- 证据：Run A（与 V0.1 逐字相同的 20 轮输入）**问句收尾、排除程序生成句** = 5/19 = 26.3%；Run B = 8/19 = 42.1%；两次合并 = 13/38 = 34.2%（带内）。同一批数据按**含问号**口径则是 40% / 68.4%（Run B 偏高）。
- 判读：单次 19 轮的样本方差很大（t3 的 84 轮语料上，同口径 46.0% 落在带内）。我不认为这构成"P1 做坏了"——但它**不满足"每次 20 轮都落在 30–50%"**这个更强的读法。
- 建议：把"20 轮"样本量提高到多次取均值（或明确写"看 3 次的中位"），并在报告里固定口径（含问号 / 问句收尾 / 是否排除程序生成句）。

### F2（high）"当前时间"这类可核查事实仍会被编造，而且不属于闸门的分类
- 证据（说话时刻取自事件日志）：
  - Run A 第 10 轮，2026-10-01T00:29:54+08:00：「凌晨**一点半**还在记事，你是准备记完就睡…」（真实 00:29；上一轮她自己刚说过"都快一点了"）
  - Run B 第 7 轮，2026-10-01T00:32:12+08:00：「**凌晨两点多**，人最容易想这些。」
  - Run B 第 16 轮，2026-10-01T00:32:52+08:00：「**凌晨三点半**还没睡着呢？」（两轮之后她自己在第 17 轮说"现在十二点半了"——同一次对话自相矛盾）
- 影响面：39 轮里 3 轮（7.7%）。**prompt 里明确给了时间**（【当前情境】"- 现在：2026-10-01T00:3x…"），所以这不是"无从得知"，而是看错了还照样说；`findUnbackedFactClaims` 的分类只有温度 / 预报指标 / 归因来源三类，**时间、日期、利率、价格、比例都不在其中**，所以这类说法原样进音频与日志。
- 铁律判断：**不是 P1 削弱了铁律**（A1 证明天气类数值照旧被拦，V0.1 也没有时间类闸门），但它是"不许编造可核查事实"的残洞，而 P1 放开长度后每轮输出的具体信息更多，暴露面更大。给 high 的理由：验收条款点名要核这一条，而这是它的活体反例，不是纸面风险。
- 建议：把"与 world state 冲突的时间/日期说法"纳入确定性校验（程序手里就有真时间，这一条最便宜也最确定）；利率/价格类数值要么进闸门，要么在提示词里明确禁止（P1 的 84 轮记录里出现过"三年期大额存单大概在2.6%上下"这类）。

### F3（medium）长回复会带 markdown 加粗与项目符号，会被 TTS 念出来
- 证据：Run B 第 17 轮（327 字，8 段）正文含 `- **别硬躺**。`、`- **手机放下**。` 等；P1 的 84 轮记录里 4/71 轮带加粗或项目符号（其中 3 轮是同一个"国债 vs 定存"理财题），V0.1 是 2/75 轮。`normalizeReplyText` 只去掉换行，`**` 与 `- ` 会原样进入分段与 TTS。
- 影响：朗读时会出现"星号星号"，恰是"像客服/像助手"的典型痕迹；且 P1 是"知识题可以多说"，这类回答的出现概率在上升。
- 建议：在说话方式里加一句"不用列表、不加粗、不用标题"，或把 markdown 符号纳入 `HARD_POLICY`/清洗（注意：清洗属于 t7 的卫生层，不要和"禁止编造"混在一处）。

### F4（medium）每段 60 字的"硬上限"在尾部合并时会被突破
- 证据：P1 的 84 轮记录里 3/71 轮出现 >60 字的单段（最长 170 字，如 `…[51,21,40,31,32,51,28,170]`）；V0.1 同样机制、最长 341 字。我的两次 20 轮是 0 轮（最长正好 60）。
- 机理（读代码）：`splitReplyIntoSegments` 先按 60 字贪心填充，段数超过 `maxSegments` 时把尾部 `splice` 合成一段，**合并后的那一段不再受 `segmentMaxChars` 约束**，只由 `mergedOverflow` 标记。而配置注释与文档写的是"硬上限 60"。
- 建议：要么让尾部合并在超出时继续切（牺牲"整句"换"不超长"），要么把注释/文档改成"目标块长，尾部合并时可能超出（`mergedOverflow`）"，并在指标里把 `overLimitTurns` 作为告警而不是脚注。

### F5（medium）1/39 轮的回复在词中间断掉，归因未定
- 证据：Run B 第 4 轮（2026-10-01T00:31:56+08:00）交付文本以「…剪的时候留神别划着手，**夜**」结束——一个不能作句末的孤字；事件日志里的 assistant 文本与交付文本一致，说明不是分段/播放环节丢字。39 轮里只此一例。
- 复现尝试（有缺陷，**未复现**）：我用 `data/verification/t4/t4-truncation-repro.ts` 从该次运行的 store 副本重建 prompt，用 `maxCompletionTokens=400` 与 `2000` 各跑一次：400 那次给出完整的 129 字、2000 那次只有 21 字（"…你这突然一句我没接上"）。**这个实验不成立的**：`buildPrompt` 取的是该会话**最近 8 轮**，而会话已跑完，取到的是末尾几轮，不是该轮当时的上下文——所以它既不能证明也不能否证 token 上限。
- 建议：在适配器里捕获并记录 `finish_reason`（尤其是 `length`），失败/截断的轮次才能被指标发现；同时对齐 §F7。

### F6（medium）文档超前于实现：铁律 3 / ADR-0011 说"硬底线之外由模型读空气决定"，代码仍由单一阈值一票否决
- 证据（**对象是 8ef37f5 的代码**）：`AGENTS.md` 铁律 3（t2 之前的提交 8569994 改的）与 `docs/adr/0011-proactive-decision-ownership.md` 写"确定性评分只提供候选与依据，**不再由单一阈值一票否决**"；而 `packages/conversation/src/proactive.ts` 的 `evaluateProactiveGates` 仍以 `SCORE_BELOW_THRESHOLD` 否决（代码里的顺序说明也仍是这一套），全库 `git grep` 也找不到"费用上限"对应的实现（`cost_cap`/`costCap`/`费用上限` 无命中）。
- 后续状态：写本报告时已有在途任务（P5）正在按 ADR-0011 重写这个文件（见 §1.4），说明这条已被接住；本条的判断只对 8ef37f5 有效。
- 判读：**不是削弱**——实现比文档更严（程序仍然拦），铁律 1/3 的"边界由程序负责"成立。但两个后果是真的：① 读代码的人会以为两层决策已经落地；② "费用上限"被写成硬底线却没有任何代码兑现，一旦有人按文档认为它已被保证，就会误判风险。
- 建议：在 ADR-0011 标注"状态：已决定 / 尚未实现（仍是 ADR-0009 行为）"，或把"费用上限"从铁律 3 的括号里去掉直到它真的存在。

### F7（low）调用侧 `maxCompletionTokens: 400` 与放开后的 480 字容量不对齐
- 证据：`scripts/chat.ts` 与其它调用侧都传 400（适配器默认值也是 400），而 P1 之后的容量是 8×60=480 字；P1 的 84 轮记录里最长回复 424 字（完整收尾，未见截断），我的 Run B 最长 327 字（完整）。
- 判读：t2 已把它列为"新的实际长度上限"，我这次**没有观察到它咬人**（4 条最长回复都以完整句子结束），所以从"实测缺陷"降级为"配置语义不清 + 潜在上限"。
- 建议：把上限调到与容量匹配的值并加一条断言/注释说明换算关系（字 vs token 不是 1:1）。

### 观察（不算 finding，但值得记录）
- **模型会编造"我记得…"式的模糊记忆**：Run B 第 9 轮答"好像……还提过石榴？"——用户从未提过石榴；第 8 轮也补了一条"我记得你之前好像提过一回，说院里那棵葡萄后来不结果了"。提示词允许并鼓励 hedging（"我记得好像……"），且 `M4 记忆` 尚未实现，所以这是设计中的空档而不是门禁漏洞；V0.1 也有同类行为，非回归。
- **V0.1 的两个缺陷在本次运行中没有复现**：天气轮的正文是 `<tool_call>` 标记（t1 记录 7/8 轮）、英文思维链被当成回复说出。我的两次运行里天气轮走的是 tool 通道、正文干净，`onNotice` 里也没有 `REPLY_HYGIENE`（0 次触发）——与 t7 的修复一致。
- **静默时段跑测试不再假红**：t1 记录过"23:30–07:30 内 `npm test` 必红 2 条"。我在 00:2x（静默窗内）实跑是 **281/281 全绿、exit 0**，说明 4c0d1d2 的时钟修复有效。

## 6. 我没测的 / 局限（不假装通过）
